консольные команды, обучение и сборку. OpenSpec используется для сверки полноты,
но запланированные там возможности не считаются готовыми, если их нет в коде.

## Установка и виртуальные окружения

Для запуска из исходников требуются Python 3.13+ и [`uv`](https://docs.astral.sh/uv/).
Зависимости разделены на несколько окружений, чтобы обычному запуску не требовались
PyTorch и тяжёлые пакеты обучения.

| Окружение | Назначение | Состав | Создание |
|---|---|---|---|
| `.venv` | Запуск GUI, классические алгоритмы и ONNX-инференс на CPU | Runtime-пакеты: PyQt6, OpenCV, NumPy, psutil, ONNX Runtime CPU | `uv sync` |
| `.venv-dev` | Тестирование и разработка без обучения нейросетей | Runtime + pytest-стек, Nuitka и zstandard; без PyTorch | `UV_PROJECT_ENVIRONMENT=.venv-dev uv sync --extra dev` |
| `.venv-full` | Обучение моделей, аугментация, сравнение архитектур и ML-отчёты | Всё из `dev` + PyTorch/torchvision, albumentations, TensorBoard, Plotly и другие ML-пакеты | `UV_PROJECT_ENVIRONMENT=.venv-full uv sync --extra full` |
| `.venv-build` | Изолированная сборка бинарника; обычно создаётся автоматически | Runtime, ONNX Runtime CPU, Nuitka и zstandard; без PyTorch | Создаётся `scripts/build_nuitka.sh` или CI |

Команды выше приведены для Bash (Linux/macOS). В Windows PowerShell переменную для
альтернативного окружения задают отдельно:

```powershell
$env:UV_PROJECT_ENVIRONMENT = ".venv-full"
uv sync --extra full
```

Подробности:

- **`.venv` — runtime.** Это минимальный вариант для обычного пользователя и
  запуска приложения из исходников. ONNX-модели выполняются через
  `CPUExecutionProvider`; PyTorch для применения моделей не нужен.
- **`.venv-dev` — разработка и тесты.** Включает pytest, pytest-qt, pytest-cov,
  hypothesis, Nuitka и zstandard, но не содержит стека обучения.
- **`.venv-full` — полный ML-цикл.** Нужен для `augment`, `train`, `train-compare`,
  `train-colony` и инструментов обучения. PyTorch использует CUDA, если она
  доступна в системе и установлена совместимая сборка PyTorch; иначе обучение идёт
  на CPU.
- **`.venv-build` — только сборка приложения.** Создаётся отдельно от остальных
  окружений и не загрязняет их. Скрипт использует `--no-sync`, чтобы `uv` не удалил
  вручную добавленные Nuitka и zstandard.

Не устанавливайте dev- или ML-пакеты в `.venv` вручную — выберите соответствующее
окружение. После обновления зависимостей или extras окружение может потребовать
повторного `uv sync`.

## Запуск и форматы изображений

### Для пользователя

Скачайте бинарник со страницы [Releases](https://github.com/Egel68/bacterial-colony-area/releases):

- Linux: `BacteriaAnalyzer`
- Windows: `BacteriaAnalyzer.exe`

Отдельная установка Python и библиотек для бинарника не нужна.

### Из исходников

```bash
uv sync
uv run bacteria-analyzer
```

Поддерживаются PNG, JPG/JPEG, BMP, TIFF/TIF и WebP. Загрузчик сначала пробует Qt,
а при ошибке декодирования использует OpenCV как резервный вариант.

### Консольные команды проекта

| Команда | Для чего используется | Обычно нужно окружение |
|---|---|---|
| `uv run bacteria-analyzer` | Запуск GUI-приложения | `.venv` |
| `uv run test-algorithms` | HTML-отчёт тестирования алгоритмов | `.venv` |
| `uv run baseline` | JSON-baseline четырёх классических алгоритмов | `.venv` |
| `uv run evaluate` | Пакетный прогон с каталогом отчёта в `evaluations/` | `.venv` |
| `uv run import-22022540` | Импорт COCO-bbox датасета 22022540 | `.venv` |
| `UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync augment` | Генерация аугментированных пар для стандартного обучения | `.venv-full` |
| `UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync python -m train.main train-colony` | Подготовка, обучение и оценка компактной COCO-модели | `.venv-full` |

Справка по параметрам: `uv run test-algorithms --help`, `uv run evaluate --help`,
`UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync python -m train.main train-colony --help`
и `UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync python -m train.main --help`.
Команды `train`, `train-compare`, `list-models` и `dataset-info` доступны как
подкоманды `python -m train.main`; для них в проекте нет отдельных console scripts.

## Анализ чашки Петри

1. В главном окне нажмите **«📂 Открыть»** и выберите изображение.
2. Нажмите **«🔍 Анализировать»**. Программа ищет чашку по ярким бликам, затем при
   необходимости применяет поиск окружности.
3. В окне анализа выберите алгоритм, настройте геометрию и нажмите
   **«🔄 Пересчитать»**.
4. Если авто-поиск ошибся, исправьте центр X/Y и радиус вручную. Кнопка
   **«Сбросить к авто-поиску»** запускает поиск заново.

### Параметры классического алгоритма

| Параметр | Диапазон | Назначение |
|---|---:|---|
| Чувствительность | 1–100% | Влияет на порог бинаризации. В текущей формуле повышение чувствительности обычно понижает порог и выделяет больше пикселей; число областей зависит от снимка. |
| Усиление контраста | 0.5–3.0× | Управляет усилением CLAHE. |
| Отступ от края | 0–30% радиуса | Сужает рабочую область до внутренней части чашки. |
| Мин. размер колонии | 1–1000 пикселей площади | Удаляет компоненты, площадь которых меньше значения (UI подписывает его `px`). |
| Заполнять сплошные зоны | вкл./выкл. | Для крупных или сливных участков. |
| Сила заполнения | 1–100 | Размер морфологического ядра при solid fill. |

Начальные значения GUI: чувствительность 50%, контраст 1.0×, отступ 8%, минимум
50 px, solid fill выключен, сила заполнения 15. Классический алгоритм извлекает
зелёный канал, усиливает контраст, подавляет фон, выполняет бинаризацию и
морфологическую фильтрацию. При найденной геометрии чашки маска детекции
ограничивается минимумом 1% отступа, даже если в поле задано 0%. У классического
режима при этом процент покрытия рассчитывается по площади чашки без отступа,
если в поле оставлено 0%. Число колоний — число связных компонент итоговой маски.

### Нейросетевые алгоритмы

В окне анализа доступны зарегистрированные алгоритмы и bundled-модели из `models/`.
В текущем проекте поставляются:

- `NN:colony_seg` — существующая ONNX-модель;
- `NN:colony_mobilenet_v3_small` — MobileNetV3-Small для полноразмерного кадра.

MobileNet обрабатывает изображение на CPU тайлами 512×512 с шагом 384 px.
Перекрывающиеся вероятности усредняются до бинаризации; края кадра тоже
покрываются. Окно показывает прогресс тайлов, пока модель работает в фоне.
Обычный ONNX-адаптер (например, `NN:colony_seg`) сначала приводит весь кадр к
размеру модели, по умолчанию 512×512, и затем растягивает маску обратно — это не
полноразмерная tiled-обработка.

При выборе NN классические настройки чувствительности, контраста, минимального
размера и solid fill отключаются. Геометрию чашки и отступ от края можно
корректировать. Внешнюю ONNX-модель можно загрузить в окне тестирования; загрузка
там не меняет автоматически список алгоритмов уже открытого окна анализа.

### Просмотр и сохранение результата

Доступны режимы:

- **Результат** — фото с наложением найденной маски и контурами областей;
- **Оригинал** — исходное изображение;
- **Предобработка** — отладочное изображение классического алгоритма после
  вычитания фона и ограничения рабочей зоной. Для ONNX-алгоритма отдельное такое
  изображение не создаётся, поэтому показывается оригинал;
- **Бинарная маска** — для классического алгоритма это морфологически очищенная
  маска до фильтрации по минимальному размеру компоненты; для ONNX — выход модели
  после ограничения рабочей зоной и отступом.

Для результата можно переключать отображение контура чашки и зелёную заливку.
Панель показывает число компонент, процент покрытия рабочей зоны и площадь маски
в пикселях. Кнопка **«💾 Сохранить»** сохраняет отображаемое изображение в PNG или
JPG; сохраняется pixmap области просмотра, поэтому размер соответствует
масштабированному изображению в окне и не гарантирует исходное разрешение.

## Ручная разметка

На главном экране нажмите **«✏️ Разметка тестовых изображений»**. В диалоге можно
создать сессию по имени, изменить корневую папку, открыть одну из недавних сессий
или выбрать существующую папку. По умолчанию сессии хранятся в
`~/BacteriaLabeling/`; путь и список последних сессий сохраняются между запусками.
Имя очищается от символов, недопустимых в файловых именах Windows, и ограничено
60 символами.

Структура сессии создаётся автоматически:

```text
<session>/
├── source/          # исходные фотографии
├── masks/           # маски исходников
├── cropped/         # обрезки чашек
└── cropped_masks/   # маски обрезков
```

### Рабочий процесс

1. Выберите **«Исходные изображения»** и нажмите **«📂 Добавить изображения»**.
   Файлы копируются в `source/` под исходными именами. Файлы назначения с таким же
   именем могут быть заменены.
2. Выберите снимок. В source-режиме запускается авто-поиск чашки. Если он не
   сработал, задайте центр и радиус вручную или попробуйте **«🔍 Авто-поиск»**.
3. При необходимости нажмите **«✂️ Обрезать по чашке»**. Обрезка сохраняется в
   `cropped/`, фон за кругом чашки становится чёрным. Файл обрезки — PNG; повторная
   обрезка снимка с тем же именем заменит прежний файл.
4. Рисуйте кистью или переключитесь на ластик. Маска бинарная: фон `0`, колония
   `255`.
5. Нажмите **«💾 Сохранить маску»**. Если маска уже есть, приложение спросит о
   перезаписи.
6. Повторите для остальных файлов. **«📦 Экспорт в ZIP»** сохраняет всю папку
   сессии с относительными путями.

Инструменты: кисть 2–100 px с шагом 2 px, очистка маски, режимы
**«Изображение + маска»** и **«Только маска»**, масштабирование кнопками или
колёсиком в пределах 0.1×–20× и сброс **1:1**.

Имена, создаваемые разметчиком:

```text
source/sample.png                  masks/sample_mask.png
cropped/sample_cropped.png         cropped_masks/sample_cropped_mask.png
```

Маски разметчика всегда сохраняются в PNG независимо от расширения исходника.
Ограничение при обучении и тестировании описано в разделе
[совместимости](#совместимость-форматов-и-ограничения).

## Тестирование алгоритмов

Тестирование доступно из главного окна и через CLI. Результат прогноза сравнивается
с эталонной бинарной маской по IoU, Dice, F1, Precision, Recall и Accuracy.

### Формат датасета для GUI и `report`

Обычная структура:

```text
test_images/
├── source/sample.png
├── masks/sample_mask.png
├── cropped/sample_cropped.png          # необязательно, вместе с маской
└── cropped_masks/sample_cropped_mask.png # необязательно
```

GUI тестирования и CLI `report` используют `TestDataset`, который ожидает
расширение маски, совпадающее с расширением изображения.

### GUI

Нажмите **«🧪 Тестирование алгоритмов»**. Выберите корень датасета, отметьте нужные
алгоритмы (по умолчанию отмечены все), при необходимости загрузите `.onnx`, задайте
размер batch и лимит исходных снимков. GUI вычисляет попарное сравнение пары,
выбранной в двух списках (по умолчанию первые два алгоритма), независимо от
галочек списка запуска; telemetry можно включить отдельно. Прогон выполняется в
фоновом потоке; после завершения показываются сводные IoU/Dice/F1/Precision/Recall
и победители сравнения по IoU/Dice/F1/Precision/Recall/Accuracy.
При включённой telemetry сводка пишется в `<data-root>/performance.json`, события —
в соседний JSONL-файл. Кнопка **«💾 Экспорт отчёта»** создаёт HTML-отчёт.

Встроенные классические алгоритмы для CLI:

| Имя | Профиль |
|---|---|
| `ClassicDefault` | sensitivity 0.5, отступ 10%, min size 50 px. |
| `ClassicHighSensitivity` | sensitivity 0.7, отступ 5%, min size 30 px. |
| `ClassicSolidFill` | sensitivity 0.3, отступ 15%, solid fill. |
| `ClassicLowSensitivity` | sensitivity 0.3, отступ 10%, min size 100 px. |

### CLI: HTML-отчёт

```bash
uv run test-algorithms \
  --mode report \
  --data-root test_images \
  --output test_report.html \
  --algorithms ClassicDefault,ClassicSolidFill \
  --model weights/another-model.onnx \
  --compare ClassicDefault,ClassicSolidFill \
  --no-per-snapshot \
  --stats-output test_report.stats.json
```

Режим `report` используется по умолчанию; запускаются все зарегистрированные
алгоритмы, выходной файл по умолчанию — `test_report.html`. Флаг `--model` можно
повторять. Имя внешней ONNX-модели в реестре берётся из имени файла без расширения.
HTML содержит таблицы и графики; расширенная статистика включена по умолчанию,
попарное сравнение добавляется при `--compare`. Графики Chart.js загружаются
браузером с CDN. CLI
`test-algorithms` регистрирует классические алгоритмы и модели, переданные через
`--model`, но не сканирует `models/` на bundled-модели.

| Флаг | Назначение |
|---|---|
| `--data-root DIR` | Корень датасета; по умолчанию `test_images`. |
| `--output FILE` | Путь к файлу отчёта; для `report` укажите `.html`. |
| `--algorithms A,B` | Алгоритмы через запятую; по умолчанию все зарегистрированные. |
| `--model FILE.onnx` | Зарегистрировать внешнюю ONNX-модель; флаг повторяемый. |
| `--compare A,B` | Включить попарное сравнение двух алгоритмов. |
| `--per-snapshot` / `--no-per-snapshot` | Включить/скрыть подробные таблицы по снимкам. |
| `--stats` / `--no-stats` | Включить/выключить расширенную статистику; по умолчанию включена. |
| `--stats-output FILE.json` | Дополнительно сохранить полную статистику в JSON. |
| `--workers N` | Ограничить число параллельных worker-ов; по умолчанию выбирается автоматически. |
| `--batch-size N` | Число пар изображение-маска в batch; по умолчанию 8. |
| `--memory-budget BYTES` | Бюджет памяти для пакетной загрузки/worker-ов. Это ориентир, не жёсткий лимит на одно крупное изображение. |
| `--sample-limit N` | Положительный лимит исходных снимков; соответствующая cropped-пара также включается, если она есть. |
| `--cache` / `--no-cache` | Кэш масок предсказаний в `<data-root>/.cache/preds/`; по умолчанию выключен. |
| `--telemetry` / `--no-telemetry` | Включить/выключить структурированную telemetry; по умолчанию выключена. |
| `--telemetry-interval SEC` | Интервал telemetry-снимков; по умолчанию 5 секунд. |
| `--performance-output FILE` | Путь JSON-сводки telemetry; события пишутся в соседний файл с суффиксом `.jsonl`. Если путь не задан, он строится от `--output`. Оба файла создаются только при включённом `--telemetry`. |

### CLI: JSON-baseline классических алгоритмов

```bash
uv run baseline --data-root test_images \
  --output classic-baseline.json \
  --no-cropped
```

Baseline всегда запускает четыре встроенных классических алгоритма; выбор `--model`
и `--algorithms` к этому режиму не применяется. Указывайте расширение `.json`:
общий парсер по умолчанию называет файл `test_report.html`, даже если содержимое
режима baseline будет JSON. `--no-cropped` отключает cropped-варианты. Доступны
также `--workers`, `--batch-size`, `--memory-budget`, `--sample-limit`, `--cache`,
`--telemetry`, `--telemetry-interval` и `--performance-output`.

### CLI: пакетный `evaluate`

```bash
uv run evaluate \
  --data-root test_images \
  --sample-limit 20 \
  --workers 4 --batch-size 8 \
  --telemetry
```

Команда запускает фиксированный набор четырёх классических алгоритмов и создаёт
`evaluations/<дата-время>/` с `report.json`, `report.html`, конфигурацией и
`run_info.json`. Это baseline-оценка, не обучение нейросети и не общий HTML-отчёт
из режима `report`.

Параметры:

- `--data-root DIR`, `--no-cropped`, `--sample-limit N` — источник и состав данных;
- `--workers N`, `--batch-size N`, `--memory-budget BYTES` — пакетная обработка;
- `--cache` — кэш масок предсказаний. Отдельно от него `evaluate` читает
  агрегированный baseline cache из `<data-root>/.cache/` только без `--sample-limit`;
- `--clear-cache` — удалить запись агрегированного кэша для `--data-root`, заданного
  в командной строке, перед запуском (это не удаляет весь каталог `.cache/preds`);
- `--telemetry` / `--no-telemetry`, `--telemetry-interval SEC`,
  `--performance-output FILE` — telemetry;
- `--config FILE` — JSON- или YAML-конфигурация;
- `--import-root DIR` — перед прогоном импортировать COCO-источник в `--data-root`.

В конфигурации используются ключи с подчёркиванием, например `workers`,
`memory_budget`, `sample_limit`, `performance_output` и `import_root`. Учтите, что
parser передаёт в конфиг некоторые значения CLI по умолчанию: `data_root`,
`use_cropped`, `use_cache`, `batch_size`, `telemetry` и `telemetry_interval` из
конфига будут заменены значениями командной строки, включая defaults. Указывайте
нужные значения этими флагами CLI, особенно `--data-root`. Для YAML нужен PyYAML;
JSON работает без этой дополнительной зависимости.
Режим `evaluate` всегда запускает четыре встроенных классических алгоритма. Он не
использует `--algorithms`, внешние `--model`, `--compare` или HTML-параметры общего
CLI; одноимённые `algorithms`, `models`, `compare` и `per_snapshot` в конфиге также
не меняют этот фиксированный набор.

Ограничение текущей реализации: `evaluate` записывает агрегированный baseline cache
и после прогона с ограниченной выборкой (`--sample-limit` или `sample_limit` в
конфиге), хотя при таком прогоне не загружает старый кэш. Это может оставить в
кэше метрики только ограниченной выборки. Не используйте ограниченный прогон перед
полным прогоном на том же датасете; если уже использовали, перед полным прогоном
запустите его с `--clear-cache`. Очистка происходит до чтения конфига и использует
`--data-root` из командной строки. Ключ агрегированного кэша учитывает относительные
имена файлов и размеры, но не содержимое файлов и режим `--no-cropped`; если файлы
изображений заменили другими того же размера или изменили режим cropped, очистите
кэш перед оценкой.

Если указан `--import-root`, COCO-данные импортируются в `--data-root` до оценки.
Выберите для `--data-root` отдельный каталог назначения, отличный от источника и
от существующих нужных данных: команда записывает туда файлы датасета.

Эквивалентный режим общего парсера: `uv run test-algorithms --mode evaluate ...`.

## Импорт COCO-датасета

Реализован импортёр для набора 22022540 с `annot_COCO.json`. Он растризует каждый
bbox во вписанный эллипс бинарной маски, декодирует и повторно записывает изображения
в самостоятельную папку и создаёт `dataset.json`. Изображения декодируются и
повторно записываются, поэтому выходные файлы не являются побайтовыми копиями. При
`--split` импортёр запрещает пересечение output с исходным каталогом; без этого
флага такой проверки нет — используйте отдельный новый каталог. Эллипсы —
приблизительные weak labels, а не ручная pixel-perfect разметка.

```bash
UV_PROJECT_ENVIRONMENT=.venv-full uv sync --extra full
UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync import-22022540 \
  --data-root datasets/22022540 \
  --output datasets/22022540_imported \
  --crop --split --seed 42 --verify
```

Параметры:

- `--data-root DIR` — обязательная папка COCO-источника;
- `--output DIR` — каталог результата; по умолчанию `<data-root>_imported`;
- `--crop` — дополнительно попытаться сделать cropped-вариант по найденному кругу;
- `--split` — записать воспроизводимый train/val/test split;
- `--seed N` — seed разбиения, по умолчанию 42;
- `--verify` — сверить количества COCO-боксов с YOLO/VOC-дублями, если они есть.

Если при `--crop` чашку на снимке не удалось найти, cropped-вариант для неё может
не появиться. При `--split` разбиение стратифицируется по категории COCO на уровне
исходных изображений; source/cropped-записи одной чашки получают один subset.
Выбирайте новый каталог результата отдельно от источника: при
`--split` это проверяется автоматически; без `--split` защита от совпадения путей
не выполняется, а файлы в существующем output могут быть перезаписаны. Источник
читается, результат записывается в отдельную папку. Для обучения используйте
корень импорта с `dataset.json`.

## Аугментация и обучение

Для команд этого раздела используйте `.venv-full`.

### Формат обучающих данных

Фабрика `load_manifest` выбирает один источник по приоритету:

1. `dataset.json` с относительными путями изображений/масок, видом записи и
   необязательным `subset`;
2. сессию разметки `source/` + `masks/` и/или `cropped/` + `cropped_masks/`;
3. legacy-структуру `images/` + `masks/` с совпадающими именами.

Поддерживаются бинарные маски. При явном `subset` обучение берёт train и val и не
перераспределяет test в эти выборки. Без subset применяется воспроизводимое
разделение train/validation. Multiclass-обучение и универсальный импортёр
произвольных внешних датасетов пока не реализованы.

### Аугментация пар

Команда `augment` не принимает аргументов. Она читает PNG из
`test_images/cropped/` и маски `*_mask.png` из `test_images/cropped_masks/`, создаёт
15 вариантов для каждой валидной пары и пишет:

```text
train/data/images/
train/data/masks/
```

Геометрические изменения применяются синхронно к изображению и маске; также
используются яркость/контраст, шум, blur и hue/saturation. Изображения без парной
маски пропускаются.

```bash
UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync augment
```

Повторный запуск создаёт те же базовые имена и может заменить ранее созданные
файлы в `train/data/`; при необходимости сохраните результат в другом каталоге.

### Обычное обучение

```bash
UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync python -m train.main list-models

UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync python -m train.main train \
  --model unet --data-root train/data \
  --epochs 200 --batch-size 8 --img-size 512 --lr 1e-3 \
  --dashboard
```

Доступные архитектуры: `unet`, `unet_small`, `mobilenet_v3_small_unet`. Параметры
подкоманды `train`:

| Флаг | По умолчанию | Назначение |
|---|---:|---|
| `--model` | `unet` | Архитектура из списка `list-models`. |
| `--epochs` | 200 | Максимум эпох; используется ранняя остановка. |
| `--batch-size` | 8 | Размер batch. |
| `--img-size` | 512 | Размер входа. |
| `--lr` | `1e-3` | Learning rate. |
| `--data-root` | `train/data` | Корень данных или манифеста. |
| `--dashboard` | выключен | Запустить веб-дашборд и TensorBoard. |
| `--dashboard-port` | 8765 | Порт веб-дашборда. |

Текущий парсер `train` **не** поддерживает `--no-augment`. Обучение создаёт
`train/runs/<model>_<timestamp>/` с checkpoint-ами, `summary.json`, TensorBoard
логами и `report.html`. При `--dashboard` веб-дашборд доступен на
`http://127.0.0.1:8765`, TensorBoard — на `http://127.0.0.1:6006`.

Подкоманды `list-models` и `dataset-info` не принимают параметров; `dataset-info`
использует настройки по умолчанию, включая `train/data`. Обычное обучение выбирает
CUDA при доступности и совместимой сборке PyTorch, иначе работает на CPU.

### Сравнение архитектур

```bash
UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync python -m train.main train-compare \
  --architectures unet,unet_small \
  --data-root train/data --eval-root test_images \
  --epochs 50 --batch-size 8
```

Для каждой архитектуры создаётся отдельный запуск, затем `best.onnx` оценивается
на парах из `--eval-root`. `compare.json` и `compare.html` записываются в
`train/runs/compare_<timestamp>/`. `--eval-root` должен содержать пары,
читаемые `TestDataset`; для независимой оценки не используйте обучающие снимки.
Хотя parser принимает `--dashboard` у `train-compare`, обработчик этого режима не
запускает dashboard — используйте его для подкоманды `train`.

### COCO → MobileNet pipeline

Одной командой создаётся split и manifest, обучается MobileNetV3-Small на патчах,
выбирается checkpoint по validation, проверяется ONNX и оценивается held-out test:

```bash
UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync python -m train.main train-colony \
  --data-root datasets/22022540 \
  --output train/colony_training \
  --seed 42 --train-ratio 0.70 --val-ratio 0.15 --test-ratio 0.15 \
  --epochs 100 --batch-size 8 --patches-per-image 4 \
  --cpu-benchmark
```

Для свежего запуска `--output` должен быть новым или пустым каталогом и отделённым
от read-only COCO-источника. При возобновлении он содержит ранее подготовленный
`dataset/` и run; `--resume-run` должен указывать на каталог внутри
`<output>/runs/`. Импортированные файлы записываются в `<output>/dataset/`, запуски —
в `<output>/runs/`. Pipeline создаёт source-записи; обучающие патчи 512×512
выбираются во время обучения и отдельно в датасет не записываются. Отдельного
флага `--crop` у этого pipeline нет. Все производные записи сохраняют subset
исходной группы; обучающие патчи сэмплируются из соответствующих записей во время
обучения.

| Флаг | По умолчанию | Назначение |
|---|---:|---|
| `--data-root` | обязательно | Каталог исходного COCO-датасета. |
| `--output` | обязательно | Корень результата с датасетом и runs. |
| `--seed` | 42 | Seed разбиения и обучения. |
| `--train-ratio`, `--val-ratio`, `--test-ratio` | 0.70 / 0.15 / 0.15 | Положительные доли; сумма должна быть 1. |
| `--epochs` | 100 | Максимум эпох. |
| `--batch-size` | 8 | Размер batch. |
| `--patches-per-image` | 4 | Патчи на исходное изображение за эпоху. |
| `--img-size` | 512 | Сейчас поддерживается только 512. |
| `--no-pretrained` | выключен | Не загружать ImageNet-веса MobileNet. |
| `--resume-run DIR` | — | Продолжить run внутри `<output>/runs`: полный checkpoint восстанавливает состояние обучения, старый weight-only файл даёт warm-start. |
| `--cpu-benchmark` | выключен | Замерить полноразмерный tiled ONNX-инференс через CPU provider на test-снимках. Без флага test-метрики считаются PyTorch-моделью на доступном устройстве. |
| `--promote-model FILE.onnx` | — | Явно скопировать полученный ONNX по указанному пути. |
| `--allow-overwrite` | выключен | Разрешить перезапись существующей promoted-модели. Legacy `models/colony_seg.onnx` защищён. |

Run включает checkpoint-ы, `summary.json` и `report.json` с метриками, split и
сведениями об обучении. `--cpu-benchmark` добавляет замеры CPU full-image
инференса. Inference в приложении остаётся CPU-only, даже если обучение шло на CUDA.

### Отдельный экспорт checkpoint в ONNX

```bash
UV_PROJECT_ENVIRONMENT=.venv-full uv run --no-sync python -m train.export_single \
  --checkpoint train/runs/unet_<timestamp>/checkpoints/best.pt \
  --output models/my_unet.onnx \
  --model unet --img-size 512
```

Поддерживаются `--checkpoint`, `--output`, `--model` (по умолчанию `unet`) и
`--img-size` (по умолчанию 512). Архитектура и размер входа должны соответствовать
checkpoint.

## Совместимость форматов и ограничения

- **Маски labeler-а всегда PNG.** Обычные загрузчики тестовых пар и
  `LabelingAdapter` ищут маску с тем же расширением, что у изображения. PNG-
  исходники и PNG-маски можно использовать напрямую. Для JPG/TIFF-исходника
  labeler сохранит `*_mask.png`, а загрузчик пары может ожидать `*_mask.jpg` или
  `*_mask.tiff`; подготовьте одинаковые расширения/имена либо опишите точные пути
  в `dataset.json`.
- **GUI и CLI `report` не читают `dataset.json`.** Они используют conventional-
  пары `source/` + `masks/`. Режимы `baseline`/`evaluate` читают importer-структуру и
  manifest; обучение также использует manifest.
- **COCO-импорт создаёт PNG-маски.** Пути к ним записаны в `dataset.json`, поэтому
  manifest-обучение и `baseline`/`evaluate` могут прочитать такие пары. Для GUI
  тестирования или `report` подготовьте пары в ожидаемой ими структуре.
- **Обучение бинарное.** Маски с несколькими классами пока не поддерживаются.
- **COCO bbox — приблизительная разметка.** Эллипс внутри bbox не является ручным
  точным контуром колонии.
- **Разные ONNX-пути имеют разные масштабы.** Только MobileNet использует tiled
  full-resolution inference; общий ONNX-адаптер уменьшает кадр до размера модели.
- **`train-compare` сам не создаёт held-out выборку.** Для воспроизводимого split и
  отдельной test-оценки используйте `train-colony`.
- **Не все идеи из спецификаций реализованы.** В частности, нет multiclass-обучения
  и универсального импортёра произвольных COCO/VOC-разметок. Команды и параметры в
  этом руководстве относятся к текущей реализации.
