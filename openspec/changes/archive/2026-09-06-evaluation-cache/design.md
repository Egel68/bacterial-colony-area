## Context

См. proposal.md — Why. Исходный код: `testing/baseline.py` (функция `run_baseline`), `testing/evaluator.py` (функция `run_evaluate`). Кэширование отсутствует: каждый вызов `run_baseline` прогоняет все 4 алгоритма по всему датасету с нуля.

## Goals / Non-Goals

**Goals:**
- Idempotentный прогон: повторный запуск `run_evaluate` / `run_baseline` на том же датасете пропускает уже посчитанные алгоритмы
- Persistent-кэш на диске, переживающий перезапуски процесса
- Автоматическая инвалидация при изменении датасета
- Прозрачность для пользователя: на каждом алгоритме видно "cached" или "running"

**Non-Goals:**
- Кэширование по-снимочных метрик (только агрегированные mean/std по source/cropped)
- Распределённое кэширование или sharing между машинами
- Изменение формата output (`evaluations/<timestamp>/report.json` остаётся без изменений)

## Decisions

### 1. Dataset signature: SHA256 от файловых метаданных

- **Что хэшируем**: для каждого файла изображения и маски (source + cropped) — `relpath:size` в лексикографическом порядке
- **Почему не content hash**: content hash потребует чтения всех файлов (738 снимков × ~20 МБ = ~15 ГБ IO) — это сведёт на нет выгоду от кэширования
- **Почему не mtime**: mtime меняется при копировании/rsync без изменения содержимого; size — достаточный индикатор для этого датасета (бинарные маски)
- **Почему не git commit**: датасет может быть импортирован без гита

```
SHA256(sorted([
  "source/sp01_img01.jpg:1234567",
  "source/sp01_img01_mask.png:234567",
  "cropped/sp01_img01_cropped.jpg:345678",
  ...
]))
```

### 2. Структура кэша

```
evaluations/
├── .cache/
│   └── a1b2c3d4e5f6...json
├── 2026-09-06_10-25-06/
│   ├── report.json
│   ├── report.html
│   ├── config.json
│   └── run_info.json
```

- `.cache/` — плоская директория, один файл на датасет
- Имя файла = hex-сигнатура (64 символа)
- Содержимое:
  ```json
  {
    "dataset_root": "/abs/path",
    "dataset_signature": "a1b2...",
    "created": "2026-09-06T11:00:00",
    "algorithms": {
      "ClassicDefault": {
        "source": {"mean_iou": 0.72, "std_iou": 0.05, "mean_dice": 0.83, ..., "num_samples": 369},
        "cropped": {"mean_iou": 0.75, ..., "num_samples": 369}
      },
      ...
    }
  }
  ```
- Формат значения алгоритма — тот же словарь, что возвращает `_mean_metrics`

### 3. Точка внедрения: `run_baseline` в `baseline.py`

`run_baseline(dataset, use_cropped=True, cache=None)`:
- Принимает опциональный словарь `cache` (загруженный из файла)
- Перед каждым алгоритмом проверяет `cache.get(algo_name)`
- Если есть — `log.info("Skipping %s (cached)", algo_name) + entry = cache[algo_name]`
- Если нет — выполняет детектирование, затем сохраняет entry в кэш и пишет файл

### 4. Точка внедрения: `run_evaluate` в `evaluator.py`

- После загрузки датасета вычисляет `signature_hash = compute_dataset_signature(data_root)`
- Загружает `cache_path = cache_dir / f"{signature_hash}.json"` если существует
- Передаёт cache в `run_baseline`
- После завершения сохраняет обновлённый кэш (если были новые алгоритмы)

### 5. CLI: `--clear-cache` в `__main__.py`

- Если флаг установлен: найти `.cache/<signature>.json` для указанного `--data-root` и удалить

### 6. Клэш не блокирует запись

- Потенциальная проблема: два параллельных процесса могут писать в один кэш
- Решение: пишем атомарно через `write + rename` (Path.write_text + Path.rename)
- При гонке выигрывает последний записавший — данные идемпотентны (одинаковый набор алгоритмов)

## Risks / Trade-offs

- [Risk] Изменение алгоритма (обновление параметров в коде) не инвалидирует кэш → [Mitigation] сигнатура датасета не включает версию кода. Если метрики посчитаны старой версией, кэш не пересчитается. Решение: добавить в сигнатуру git-commit. Но это сломает кэширование при любом коммите. Принятое решение: пользователь вручную использует `--clear-cache` после обновления алгоритмов.
- [Risk] Размер файла не меняется при замене изображения другим того же размера → [Mitigation] маловероятный сценарий; в этом датасете файлы не перезаписываются без удаления
- [Trade-off] Content-hash дал бы 100% точность, но требует полного чтения всех файлов (~15 ГБ) — это ~5-10 минут лишнего IO при каждом запуске даже для кэшированных датасетов. Выбран size-based signature ради скорости.
