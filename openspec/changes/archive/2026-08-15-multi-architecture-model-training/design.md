## Context

Текущее состояние модуля `train/`:

- `training/config`: `TrainingConfig` (dataclass) с `model_name="unet"`, `data_root="train/data"`, `device="cuda"`, `dashboard`, `dashboard_port`.
- `training/dataset`: `ColonyDataset` читает пары по совпадающим именам из `data_root/images/` + `data_root/masks/`; `make_datasets` делит на train/val (seed=42), бросает `FileNotFoundError` при пустоте.
- `training/models`: реестр `@register_model`/`get_model`/`list_models`; зарегистрирована одна архитектура `unet` (`UNet`, 4 down/up блока, `features=(64,128,256,512)`), наследует `BaseSegmenter`.
- `train.py`: `run_training(cfg, progress_callback)` — цикл эпох, AdamW + CosineAnnealingLR, `best.pt`/`best.onnx` по val IoU, `last.pt`/`last.onnx`, TensorBoard, early stopping, `summary.json`, экспорт ONNX (`opset=18`), метрики в реальном времени (rich/dashboard).
- `testing/`: `TestDataset` (source+masks, cropped+cropped_masks), `OnnxModelAlgorithm`, `compute_segmentation_metrics`, CLI `test-algorithms`.
- Модуль разметки формирует сессию: `source/`, `masks/`, `cropped/`, `cropped_masks/`, маски `{stem}_mask.ext` / `{stem}_cropped_mask.ext`.
- `test_images/` повторяет структуру сессии и консьюмится `testing.TestDataset` без конверсии.

**Решение о повороте:** радикальная переработка. Вместо «ядро обучения знает про форматы и угадывает структуру папок» вводится **контракт данных**: обучение потребляет пары + манифест (индекс с метаданными). Каждый источник данных — это адаптер, порождающий контракт. Задел на внешние данные (COCO/VOC/произвольные пары) — через импортёры, реализуемые в будущем, но контракт и документация проектируются сейчас.

## Goals / Non-Goals

**Goals:**
- Контракт данных: датасет = пары `(image, mask)` + манифест `dataset.json` (метаданные, `mask_mode`, `subset`, страна происхождения).
- Родной адаптер структуры разметки: сканирует `source/`+`masks/` и `cropped/`+`cropped_masks/`, суффикс `_mask`, без копирования → манифест на лету.
- Поддержка легаси `images/`+`masks/` через общий адаптерный механизм (не «особый случай» в ядре).
- Две стратегии хранения файлов: `reference` (манифест ссылается на файлы по относительному пути) и `copy` (файлы материализуются в `data_root`).
- `mask_mode`: поддерживается `binary` сейчас; поле в манифесте резервирует `multiclass` на будущее, валидация даёт понятную ошибку при несовместимости.
- Минимум две параметризуемые CNN-архитектуры (`unet`, `unet_small`).
- Метрики в реальном времени по каждой эпохе; обучение на CUDA с фолбэком на CPU; ONNX-экспорт для CPU-инференса.
- Конвейер `run_train_compare` + CLI `train-compare`: обучить список архитектур, оценить `best.onnx` на `TestDataset`, сводный JSON + HTML.
- Зафиксировать в документации (`AGENTS.md`) идею импортёров и контракта, чтобы задел не потерялся.

**Non-Goals:**
- Реализация импортёров внешних форматов (COCO/VOC/произвольные) — только проектирование контракта и документация.
- Изменение `testing/` API (переиспользуем как есть).
- Multiclass-обучение сейчас (маски бинарные; поддержка классов — задел в контракте).
- Новая структура run-директорий и формата чекпоинтов.
- Автоматический подбор гиперпараметров, кросс-валидация, распределённое обучение, GUI для обучения.

## Decisions

### D1. Контракт данных: манифест + пары

Канонический датасет описывается манифестом `dataset.json`:

```jsonc
{
  "name": "my-session",
  "origin": "labeling",        // labeling | legacy | external (задел)
  "mask_mode": "binary",       // binary | multiclass (задел)
  "storage": "reference",      // reference | copy
  "samples": [
    {
      "id": "X",
      "kind": "source",        // source | cropped | augmented
      "image": "source/X.png", // относительный путь от data_root
      "mask": "masks/X_mask.png",
      "subset": "train",       // train | val | test | null
      "dish": {"cx": 640, "cy": 512, "r": 400}  // опционально, задел
    }
  ]
}
```

Записи `samples` — единый контракт: пара `(image, mask)` + метаданные. Обучение никогда не читает папки «напрямую» — оно потребляет записи из манифеста. Пути в манифесте относительны к `data_root`.

**Почему:** манифест отделяет «что есть данные» от «как они разложены на диске». Любой источник (разметка, легаси, будущие внешние) может породить записи с одинаковым контрактом. `subset` в данных делает train/val/test явным (внешние датасеты приходят со своими сплитами), а seed-сплит остаётся фолбэком.

### D2. Адаптеры источников вместо угадывания в ядре

Вводится `train/dataset_adapters.py` с фабрикой `load_manifest(data_root) -> DatasetManifest`:

1. Если в `data_root` есть `dataset.json` → `ManifestAdapter` (читает и валидирует манифест).
2. Иначе если есть `source/` (структура разметки) → `LabelingAdapter`: сканирует `source/*.ext` + `masks/{stem}_mask.ext` и `cropped/*.ext` + `cropped_masks/{stem}_cropped_mask.ext`, составляет манифест в памяти (`storage="reference"`, без копирования), отбрасывает пары без маски.
3. Иначе если есть `images/` (легаси) → `PairsAdapter`: `images/*.png` + `masks/*.png` по совпадающим именам.
4. Если пусто → `FileNotFoundError`.

Каждый адаптер реализует единый метод `build(data_root) -> DatasetManifest`. `mask_mode` в манифесте из про-папа: для разметки/легаси — `binary`. Валидация контракта: если `mask_mode != "binary"`, `make_datasets` бросает понятную ошибку (задел: при появлении `multiclass` здесь добавится ветвление).

**Почему:** ядро обучения перестаёт ветвиться по форматам — ветвление выносится в адаптеры, что делает добавление новых источников точечным и масштабируемым. `LabelingAdapter` — прямой мост «разметили → учимся». `PairsAdapter` сохраняет работу с `train/data`.

### D3. Стратегии хранения файлов: reference и copy

Манифест поддерживает обе стратегии (`storage`):

- `reference` — файлы остаются на своих местах, манифест ссылается на них относительными путями. Родной режим для сессий разметки (`LabelingAdapter` порождает reference-манифест на лету) и для `test_images/`.
- `copy` — при импорте файлы копируются в `data_root` (например в `data_root/images/` + `data_root/masks/`), датасет становится самодостаточным и переносимым. На будущее: эту материализацию выполняют импортёры (`import_to(root)`), контракт уже описывает `storage`.

Сейчас реализуется только чтение обоих видов существующих данных; *запись* `copy` появится вместе с импортёрами. Поле `storage` хранится в манифесте и валидируется на известные значения.

**Почему:** два варианта — ответ на вопрос «копировать или ссылаться». `reference` дёшев и не дублирует файлы; `copy` даёт переносимость. Поддержка обоих в контракте снимает необходимость выбирать заранее.

### D4. mask_mode: binary сейчас, multiclass — задел

`mask_mode` описывает представление маски. Сейчас поддерживается только `"binary"` (один класс, значения 0/255). Валидация манифеста принимает `binary`; `multiclass` — известное значение, резервируемое на будущее (при попытке обучать multiclass-манифест текущим ядром — понятная ошибка «не поддерживается»). `TrainingConfig` может получить поля `mask_mode` для переопределения/проверки.

**Почему:** закладываем расширяемость без стопора: контракт уже знает о классе, потеря/метрики (`BCE` сейчас) остаются бинарными, но точка расширения явно задокументирована в схеме и в `AGENTS.md`.

### D5. Дополнительная архитектура `unet_small`

В `train/models/` добавляется `@register_model("unet_small")` — та же U-Net-структура с уменьшенным набором каналов (`features=(32, 64, 128, 256)`). Параметры (`n_channels`, `n_classes`, `features`) прокидываются через `get_model(name, **params)`. `BaseSegmenter` наследуется без изменений.

**Почему:** минимальное безопасное расширение реестра, добавка контрольного варианта для сравнения, без новых зависимостей.

### D6. Метрики в реальном времени и устройство (каркас прежний)

`run_training` остаётся ядром: `progress_callback` (rich/dashboard) + `SummaryWriter` каждую эпоху; устройство `cuda` при `torch.cuda.is_available()`, иначе `cpu`; экспорт `to_onnx` на активном устройстве. `TrainingConfig` получает поле `architectures` для compare-режима. Отдельных правок механизма метрик не требуется.

### D7. Конвейер `run_train_compare` и CLI `train-compare`

Новый модуль `train/compare.py`:

- `run_train_compare(architectures, cfg, eval_root, data_root)`:
  1. Для каждой архитектуры клонирует `cfg` (`dataclasses.replace(cfg, model_name=arch)`), вызывает `run_training(cfg_i, progress)`.
  2. Для каждой run-директории берёт `checkpoints/best.onnx`, создаёт `OnnxModelAlgorithm(path)`.
  3. Оценивает на `TestDataset(eval_root)` через `run_algorithm` (source+cropped), усредняет метрики (с числом снимков).
  4. Собирает `{arch: {iou, dice, precision, recall, f1, n}}`, сохраняет `compare.json` и `compare.html` (inline-таблица, без новых зависимостей) в `train/runs/compare_{timestamp}/`.
- CLI в `train/main.py`: `train-compare` с `--architectures unet,unet_small`, `--data-root`, `--eval-root`, общими параметрами (epochs, batch-size, img-size, lr, dashboard).

**Почему:** переиспользует `run_training`, `OnnxModelAlgorithm`, `run_algorithm`; оценка на реальных тестовых парах даёт честное сравнение архитектур.

## Risks / Trade-offs

- **Смена концепции данных ломает существующий вызов `make_datasets(train/data, ...)`**: компенсируется `PairsAdapter`, сохраняющим прежнее поведение; автотесты/ручные прогоны проверяют нерегресс.
- **Манифест как новый артефакт**: риск несогласованности путей. Митигируется: пути обязаны быть относительными и проверяться при валидации; `LabelingAdapter` генерирует манифест на лету, файл `dataset.json` необязателен.
- **`unet_small` как скромное расширение**: пользователь может добавить любую архитектуру через `@register_model`; конвейер работает с любой зарегистрированной моделью.
- **Оценка через `run_algorithm` включает source и cropped**: метрики агрегируются по снимкам; в отчёте указывается `n` снимков.
- **Задел multiclass/importers не реализуется сейчас**: риск «потери идеи» снят документацией (design.md + AGENTS.md) и полями контракта; такие задачи зарезервированы на будущее без изменения ядра.
- **Производительность**: последовательное обучение нескольких архитектур ожидаемо дольше; ускорение не входит в цели.
