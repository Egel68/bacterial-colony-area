# Spec-Driven Development (OpenSpec Integration)

## Overview
Ты используешь спецификации как единый источник истины. Код без спецификации — это гадание. В этом проекте мы используем фреймворк **OpenSpec** для управления спецификациями.

## When to Use
- Начало новой фичи или рефакторинга.
- Требования неоднозначны.
- Изменение затрагивает несколько модулей.

## The Gated Workflow (Адаптировано под OpenSpec)

### Phase 1: Specify (Делегировано OpenSpec)
**ЗАПРЕЩЕНО:** Создавать файлы `tasks/plan.md` или `spec.md` вручную.
**ДЕЙСТВИЕ:** Вместо этого, сгенерируй и выполни команду OpenCode:
`/opsx:propose "<краткое описание задачи, включая ключевые требования и контекст>"`

Это автоматически создаст структуру:
- `openspec/changes/<id>/proposal.md`
- `openspec/changes/<id>/specs/<feature>.md`
- `openspec/changes/<id>/design.md`
- `openspec/changes/<id>/tasks.md`

Если пользователь не дал достаточно контекста, задай уточняющие вопросы (как в оригинальном скилле `interview-me`), но финальный артефакт всегда должен быть создан через `/opsx:propose`.

### Phase 2: Plan & Tasks (Управление через OpenSpec)
После того как пользователь одобрил proposal, OpenSpec уже содержит `tasks.md`. Твоя задача — прочитать этот файл и подтвердить, что задачи атомарны (каждая ≤ 5 файлов, имеет четкий критерий приемки). Если нет — предложи пользователю обновить задачи через OpenSpec.

### Phase 3: Implement (Здесь вступают в силу остальные скиллы Addy)
Выполняй задачи строго по одной, используя скиллы:
- `test-driven-development`: Сначала пиши тест, который падает.
- `incremental-implementation`: Делай маленькие коммиты.
- `browser-testing-with-devtools` или `debugging-and-error-recovery`: Для верификации.

## Common Rationalizations (Анти-отговорки)
| Отговорка агента | Жесткий ответ (Rebuttal) |
|---|---|
| "Это просто, я напишу код сразу, а спецификацию потом" | Нет. Сначала `/opsx:propose`. Спецификация фиксирует договоренности до написания кода. |
| "Я пропущу тесты, чтобы сделать быстрее" | Нарушение правила `test-driven-development`. Тесты — это доказательство (evidence requirement). |
| "Я изменю архитектуру без обновления spec" | Нарушение правила OpenSpec. Сначала обнови `design.md` через OpenSpec, потом код. |

## Verification
Перед тем как сказать "Задача выполнена", ты обязан предоставить доказательства:
1. Вывод команды `openspec validate` (или подтверждение, что структура `openspec/` цела).
2. Вывод успешного запуска тестов (`npm test` / `pytest` и т.д.).
3. Подтверждение, что все чекбоксы в `openspec/changes/<id>/tasks.md` отмечены.
