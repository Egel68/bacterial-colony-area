## Context

См. `proposal.md` — Why. Текущий batch scheduler в `testing/scheduler.py` последовательно декодирует batch, затем создаёт новый `ThreadPoolExecutor` для алгоритмов; telemetry объединяет чтение и декодирование в `load`. `memory_budget` учитывает только входные массивы batch, но не резерв временных буферов конкурентных детекций и не ограничивает RSS. Парное сравнение из `ui/testing_window.py` повторно вызывает `compare_algorithms()` после полного прогона.

В измеренном окружении JPEG/маски 369 source-пар декодировались примерно 17 с последовательно и примерно 2,9 с при 12 потоках на заранее прочитанных bytes; три крупнейших кадра (~35 MP) с четырьмя классическими алгоритмами загружались менее секунды при 135–180 с вычислений. Это не холодный I/O benchmark. Наблюдался пиковый RSS до ~3,4 GiB при шести внешних workers. Для одного крупного кадра Hough circle search и повторный полный проход по карте компонентов занимали значимое время; экспериментальная замена прохода по компонентам lookup-операцией дала эквивалентную маску, но требует проверки на наборе данных.

GUI-тестирование и tiled NN уже используют фоновые Qt threads, однако начальная загрузка и классический анализ в `AnalysisWindow`, операции выбора/автопоиска/обрезки/рисования и копирование/ZIP в разметке, экспорт HTML и построение сравнительной таблицы происходят из UI-обработчиков. Отдельный тест отзывчивости есть для tiled NN, но нет общего heartbeat acceptance для этих путей. `utils/image_loader.py` использует QPixmap до OpenCV fallback; этот порядок нельзя безоговорочно переносить в worker, так как QPixmap — GUI-ресурс. Фоновое декодирование должно использовать thread-safe путь на базе QImage и сохранять договорённости о форматах, BGR-порядке и fallback.

## Goals / Non-Goals

**Goals:**

- Собрать репрезентативную, воспроизводимую производительность и корректность на тестовом наборе, включающем обычные и крупные source/cropped кадры.
- Использовать единый конечный ресурсный бюджет для входных массивов, декодеров, внешних algorithm workers и native thread pools; не насыщать память неограниченным prefetch.
- Разделить измерения физически доступных системных I/O counters, логического чтения, декодирования и вычислительных стадий; измерять ожидание входа независимо от очереди CPU-задач.
- Устранить подтверждённую лишнюю работу классического пути и повторное выполнение детекции для парного сравнения, только когда можно доказать эквивалентность.
- Перенести тяжёлые операции всех затронутых GUI-сценариев из event loop и иметь устойчивый протокол состояния, ошибки, отмены и закрытия.

**Non-Goals:**

- Линейное ускорение, единый оптимальный worker count либо гарантированный абсолютный throughput на всех компьютерах и типах хранилища.
- Неограниченное увеличение concurrency, полная фиксация RSS ниже целевого memory budget для неизвестных native allocations, либо обязательная загрузка всего корпуса в RAM.
- Изменение параметров сегментации, качества масок/метрик, выходных форматов, dataset contracts или используемой по умолчанию модели.
- Введение multiprocessing или shared-memory транспорта без замеров, показывающих, что потоки/native libraries не обеспечивают нужный throughput.
- Изменение точности, размеров и семантики ручной разметки. Внутреннее представление canvas/перерисовка могут быть оптимизированы, но full-resolution маска и координаты кисти остаются точными.

## Decisions

### 1. Сначала оптимизировать подтверждённую дублирующую работу

Для выбора профиля и классического анализа измерять отдельными стадиями поиск чашки, фильтрацию компонентов и общую предобработку. Рассматривать векторизацию фильтра connected components и общий per-sample context для геометрии/неизменяемых стадий. Такой context SHALL различать source/cropped, входное содержимое, геометрию и параметры, влияющие на стадию. Не переиспользовать результат, если параметр меняет threshold, ROI, morphology или иной наблюдаемый output. Зафиксировать эталонные бинарные маски и сравнить bitwise до/после на обычных, крупнейших и пограничных кадрах.

Для интегрированного сравнения A/B использовать результаты основного прогона, если совпадают dataset selection, variant, model/algorithm parameters и cache identity. Если алгоритм не выбран для основного набора, запустить только недостающую задачу сравнения один раз. Существующий CLI/API сравнения вне общего прогона остаётся совместимым.

**Альтернативы:** сначала вводить process pool — отвергнута как первая мера, потому что наблюдаемая работа выполняется главным образом в OpenCV/ONNX native code, а процессы требуют передачи крупных arrays или повторного чтения. Слепо кэшировать весь `detect()` — отвергнуто из-за различий параметров между алгоритмами и риска изменить семантику.

### 2. Ограниченный двухстадийный loader/compute pipeline

Оставить текущую bounded batch-модель как корректный baseline и добавить producer-consumer overlap с небольшой ограниченной очередью подготовленных sample/batch. Чтение bytes и decoder concurrency измерять раздельно: файловое чтение может ждать медленного диска, а декодирование само является CPU-задачей. Префетч следующего входа разрешать только если планировщик зарезервировал память и общий CPU budget; очередь блокирует producer при backpressure. Декодированные image/mask массивы разделять между алгоритмами как read-only. Один sample больше memory target обрабатывать изолированно; следующий batch не загружать до его освобождения.

**Альтернативы:** загрузить все снимки заранее — отвергнута, потому что source batch восьми пар уже измерялся до ~795 MiB, а корпус содержит изображения до ~35 MP; неограниченный producer pool — отвергнут из-за пиков RSS. Чистый `asyncio` не выбран: чтение/декодирование и алгоритмические API синхронные, поэтому нужен bounded executor/queue, а не event-loop кооперативность.

### 3. Один ресурсный менеджер для outer/native concurrency

Определять доступную конкурентность от affinity/quota процесса, а не только `os.cpu_count()` или физического числа host CPU. Внешние workers, loader threads и внутренние OpenCV/ORT pools считать частями одного бюджета. Для CPU-bound interactive app background tasks иметь более низкий/ограниченный budget или зарезервированную долю доступной мощности для GUI; политика должна оставаться безопасной, если сведения об affinity/quota недоступны. `--workers` остаётся пользовательским максимумом, не гарантией фактического числа параллельных задач.

Классические алгоритмы и tiled ONNX требуют разной concurrency: OpenCV классика уже создаёт native parallel work, а измеренная tiled модель с одним внешним заданием использовала около 11 CPU cores благодаря ONNX Runtime. Поэтому не фиксировать повсеместный `cv2.setNumThreads(1)` и не создавать одну ORT-сессию на каждый image worker до A/B benchmark; тюнинг проводить на нескольких dimensions и типах алгоритма.

**Альтернативы:** резервировать фиксированное ядро на всех машинах — отвергнуто как непереносимое на CPU с 1–2 ядрами; всегда использовать все cores — отвергнуто из-за требования отзывчивости GUI и измеренных latency/RSS regressions при высокой конкуренции.

### 4. Telemetry измеряет причинные стадии, а не подменяет I/O CPU-временем

Добавить отдельные stage timers/logical byte counters для file read, imdecode, wait-for-input, submit-to-start queue wait, detect, metrics, report и end-to-end. Фиксировать process CPU-time/wall-time как core-equivalents, доступные CPU/affinity/quota, выбранные outer/native worker limits, RSS snapshots/peak и активную/ожидающую работу. OS physical read-byte counters оставлять отдельными capability counters: ноль может означать page cache, а не отсутствие `read()`/I/O latency. Не выполнять disk-cache drop на машине пользователя как часть тестирования; cold-storage acceptance проводить только в явно контролируемой среде.

Прогресс основного прогона и сравнения строить на фактически завершённых задачах, включая ошибки/отмены; не интерпретировать queue wait как input starvation. Долю input-starvation считать по worker-slot-seconds: время, когда slot готов взять задание, но очередь входов пуста, делённое на доступные slot-seconds активной фазы алгоритмов; исключить startup/shutdown и намеренно сериализованные lane. В качестве pinned CPU-bound acceptance-профиля использовать reference dataset и reference environment с целью <=5%. Если профиль не достигнут, сначала анализировать сам профиль, а не скрывать bottleneck увеличением workers.

### 5. Общий контракт фоновой GUI-операции

Длительную операцию представлять единым lifecycle: immutable snapshot входов/параметров при старте → worker без обращения к widgets → queued status/progress/result/error signals → применение результата только для всё ещё актуального selection/generation id → очистка worker/кнопок. UI widgets и QPixmap создавать/менять только в GUI-потоке; для фоновой загрузки использовать thread-safe decoder (QImageReader/QImage или OpenCV), не вызывать QPixmap из worker. В пределах одного labeling selection переиспользовать уже декодированное BGR-изображение для автопоиска/обрезки вместо повторного открытия исходного файла. Использовать cooperative cancellation между безопасными единицами работы; native OpenCV/ORT вызов может быть не прерываемым, поэтому запрос отмены не должен вызывать блокирующий GUI wait. При отмене/закрытии показать состояние завершения, отменить ещё не начатую работу и закрыть окно после безопасного возврата текущего native-вызова, без блокирующего ожидания в event loop.

В analysis окне вынести декодирование, поиск чашки, начальный и повторный classic/NN анализ, тяжёлое композитирование/масштабирование изображения и запись результата из конструктора/слотов. Сохранение SHALL оставлять прежнее наблюдаемое поведение `QPixmap.save`: содержимое и размеры snapshot отображённого pixmap на момент команды, с кодированием по выбранному расширению. В labeling окне вынести чтение image/mask, обновление большого списка файлов, auto-detect, crop, multi-file copy, запись маски и ZIP. Для одного labeling selection повторно использовать уже декодированный оригинал. В testing вынести report generation и большие операции подготовки presentation; для больших сравнений использовать представление, которое не требует создавать один виджет на каждую ячейку синхронно. Полноразмерные image/mask arrays сохранять для анализа/разметки, но формировать отображаемое представление в границах viewport; движение кисти должно менять full-resolution mask локально и не пересобирать целый кадр на каждое событие мыши. Массовые представления обновлять порциями или через модель/view; сохранить пиксельную точность и zoom semantics.

**Альтернативы:** делать CPU work в UI через короткие timers — отвергнута, так как OpenCV/ORT synchronous native call нельзя надёжно разделить так; запускать процесс на каждое нажатие — отвергнута из-за цены старта, копирования массива и сложности отмены.

### 6. Performance acceptance и эквивалентность

При начале реализации снять и сохранить reference-профиль доступной машины/OS, версий OpenCV/ORT, affinity/quota, RAM, размеров кадров и warm-cache state; change не устанавливает минимальный поддерживаемый класс hardware и не обещает абсолютный throughput на произвольном устройстве. Использовать одни и те же выбранные source/cropped пары, включая минимум несколько 20–35 MP images, детерминированный порядок, warm-up и повторные чередуемые конфигурации. Сравнивать последовательно и консервативно параллельно по end-to-end wall time, process CPU, stage latency, samples/sec и peak RSS. Отдельно публиковать быстрый smoke тест и полный performance набор; не делать full dataset длительным обязательным тестом CI.

GUI acceptance запускать heartbeat timer с периодом 50 ms и во время representative image-open/classic analysis/NN, labeling auto-detect/copy/export, testing run/table/report; reference p95 interval <=100 ms и max <=250 ms. Вне reference environment проверять event-loop liveness и отсутствие synchronously executing heavy work, но не трактовать абсолютные latency как аппаратную гарантию.

## Risks / Trade-offs

- [Loader threads ускоряют decode, но конкурируют с detect за те же CPU cores] → включать их только через общий budget, ограниченную очередь и end-to-end benchmark; сравнивать throughput вместе с GUI heartbeat.
- [Большие native temporary buffers превышают размер входных arrays] → memory target явно определить для in-flight decoded inputs; отдельно измерять RSS и рассчитывать conservative per-operation headroom; не заявлять жёсткий RSS cap без allocator/runtime контроля.
- [Reuse геометрии или preprocessing меняет результаты при отличающихся настройках] → ключевать context по input/variant/geometry и релевантным параметрам; проверять exact masks и метрики на representative corpus.
- [Qt cancellation не может прервать выполняющийся native call] → проверять cancellation между файлами/batches/tiles, инвалидацию позднего результата и отсутствие блокирующего wait в GUI; окно сохраняет чёткое состояние «завершение/закрытие ожидает безопасной точки» там, где требуется cleanup.
- [QPixmap/widget updates остаются дорогими на очень крупных frames] → профилировать GUI repaint отдельно, ограничивать viewport display size и копии; GUI benchmark включает кадры ~35 MP.
- [Изменение внутренней конкурентности ухудшает производительность на конкретной системе] → оставить auto mode и CLI upper bound, логировать эффективные лимиты, сохранять воспроизводимый sequential fallback.
- [Новые метрики существенно различаются между Windows/Linux и filesystem counters] → capability flags, logical operation timers, общий heartbeat тест и platform-specific raw counters без ложного сведения неизвестного к нулю.

## Migration Plan

1. Зафиксировать baseline на synthetic/малых парах и выбранном reference наборе обычных и крупных кадров; записать mask hash, метрики, stages, CPU/RSS и GUI heartbeat.
2. Добавить и проверить причинную telemetry и ограничение ресурсных лимитов, сохраняя старый последовательный/worker=1 путь как fallback.
3. Оптимизировать подтверждённые повторные проходы и совместное сравнение; пройти проверки точного равенства масок и метрик до включения ускоренного пути.
4. Добавить ограниченное перекрытие decode/compute и провести matrix outer/native worker counts; включить auto policy только после проверки отсутствия регрессии end-to-end throughput, памяти и GUI liveness.
5. Перенести GUI операции по областям (analysis, testing/report/results, labeling), включая прогресс, stale-result guard, cancellation и безопасное закрытие; принимать каждую область с heartbeat и сценариями ошибок.
6. Выполнить regression suite, smoke benchmark и отдельный полный reference benchmark. При регрессии отключить overlap/новую оптимизацию конфигурацией, сохранить старый API и последовательный fallback; форматы отчётов и пользовательские dataset файлы не мигрируют. В GUI оставить auto-policy без ручных controls; текущую политику перезаписи при копировании файлов с совпадающим именем сохранить. Benchmark host profile записать перед performance acceptance. Во время длинных операций предоставить отмену на безопасных границах; при закрытии окна показать «Завершение…», продолжать обработку событий и автоматически закрыть окно после безопасной точки отмены. Отменённые ZIP/HTML exports не публиковать под итоговым путём; прежнее содержимое итогового файла при ошибке/отмене сохранять.
