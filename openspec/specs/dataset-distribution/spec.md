# dataset-distribution Specification

## Purpose

Обеспечивает локальную проверку и подготовку обучающих датасетов, их передачу через GitHub в lossless-архивах Git LFS и восстановление файлов по путям, ожидаемым обучающим конвейером.

## Requirements

### Requirement: COCO-источник проверяется до подготовки и упаковки
Процесс подготовки SHALL проверить каждое COCO-изображение, имеющее разметку: файл существует, декодируется и соответствует размерам в аннотации. При пропущенном, повреждённом или несовпадающем по размеру файле подготовка SHALL завершиться ошибкой до создания архива.

#### Scenario: Все размеченные изображения доступны
- **WHEN** пользователь запускает локальную подготовку COCO-датасета
- **THEN** проверка SHALL охватить все идентификаторы изображений, используемые аннотациями, и подтвердить наличие, декодируемость и совпадение размеров каждого файла до упаковки

#### Scenario: Изображение отсутствует или не читается
- **WHEN** COCO-аннотация ссылается на отсутствующий, повреждённый или не соответствующий указанным размерам файл
- **THEN** подготовка SHALL сообщить путь и причину ошибки, SHALL не создать готовый архив и SHALL не отправлять данные в Git LFS

### Requirement: Обучающий набор материализуется до упаковки
Локальный этап подготовки SHALL создать все файловые пары изображения/маска, манифест набора и воспроизводимый split до архивации. Если для эксперимента требуются чёрнофоновые варианты, они SHALL быть сохранены до упаковки; вариант и исходник SHALL иметь одинаковый subset.

#### Scenario: Подготовлен полный набор для эксперимента с чёрным фоном
- **WHEN** пользователь подготавливает COCO-датасет для обучения с чёрнофоновыми вариантами
- **THEN** локальный результат SHALL содержать все исходные изображения, бинарные маски, варианты с чёрным фоном, `dataset.json` и `split.json`, а все пути манифеста SHALL разрешаться в существующие файлы

#### Scenario: Производные изображения остаются в исходном split
- **WHEN** для исходного изображения создаётся производный обучающий вариант
- **THEN** исходная и производная записи SHALL иметь один и тот же subset (`train`, `val` или `test`)

### Requirement: Подготовленные данные хранятся в lossless-архиве Git LFS
Бинарные файлы готового обучающего набора SHALL передаваться в Git LFS внутри lossless-архива `.tar.zst`, а не как отдельные распакованные LFS-объекты. Распакованные файлы SHALL побайтно совпадать с подготовленным набором. Небольшие текстовые манифесты и аннотации SHALL оставаться доступными в обычном Git; копии метаданных внутри архива SHALL совпадать с ними.

#### Scenario: Архивирование не меняет подготовленные файлы
- **WHEN** подготовленный обучающий набор упаковывается в `.tar.zst` и затем распаковывается
- **THEN** каждый файл SHALL иметь те же байты, что и до упаковки, все пути манифеста SHALL разрешаться, а встроенные копии метаданных SHALL совпадать с версиями в Git

#### Scenario: Пользователь явно отправляет архив
- **WHEN** пользователь проверил архив, доступ к репозиторию, квоту Git LFS и лицензию данных
- **THEN** документация SHALL описывать явные команды Git для добавления и отправки архива, а инструменты подготовки SHALL не выполнять эти команды автоматически

### Requirement: Получение и распаковка восстанавливают готовый датасет
После установки Git LFS и получения LFS-объектов пользователь SHALL иметь возможность распаковать архив в документированный локальный каталог, где доступны все файлы и метаданные, необходимые обучающему конвейеру.

#### Scenario: Новый checkout восстанавливает обучающий набор
- **WHEN** разработчик клонирует репозиторий с активированным Git LFS, выполняет `git lfs pull` и распаковывает архив
- **THEN** файлы изображений, масок и метаданных SHALL находиться по путям, указанным в манифесте готового набора

#### Scenario: Клонирование без Git LFS
- **WHEN** разработчик получает репозиторий без установленных или активированных фильтров Git LFS
- **THEN** документация SHALL объяснять, что вместо архива может присутствовать LFS-указатель, и описывать установку Git LFS, `git lfs pull` и распаковку

### Requirement: Документированы подготовка и ограничения распространения
Документация проекта SHALL описывать локальную проверку, материализацию и упаковку датасета, получение архива и его распаковку. Она SHALL предупреждать, что квота GitHub зависит от тарифа аккаунта и что лицензия данных должна разрешать публикацию.

#### Scenario: Новый разработчик подготавливает или получает данные
- **WHEN** разработчик выполняет документированные инструкции на новой машине
- **THEN** он SHALL иметь возможность проверить исходные изображения, создать либо получить готовый набор и запустить обучение с существующим контрактом манифеста

#### Scenario: Пользователь проверяет ограничения перед отправкой
- **WHEN** пользователь готовится отправить архив с датасетом
- **THEN** документация SHALL направлять его к актуальным условиям GitHub Git LFS и SHALL требовать проверки лицензии/атрибуции, не обещая фиксированную квоту аккаунта

### Requirement: Остальные данные репозитория остаются без изменений
Настройка распространения SHALL оставить небольшие фикстуры `test_images/` в обычном Git и SHALL сохранить игнорирование сгенерированных `train/data/` и `train/runs/`.

#### Scenario: Архивирование датасета не переносит фикстуры и результаты обучения
- **WHEN** подготовленный датасет сохраняется в Git LFS
- **THEN** `test_images/` SHALL оставаться обычным содержимым Git, а сгенерированные результаты обучения SHALL оставаться игнорируемыми
